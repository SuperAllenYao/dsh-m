# DSH-m v0.2.5

## 中文

DSH-m v0.2.5 是冷启动与列表刷新性能版本：在 5G、手机与 Mac 不同网络的真机场景下，把「连接中 → 在线」从 2.4–2.7 秒降到 **0.63–0.72 秒（10/10 <1s）**，并让工作区列表在 1 秒内就绪、不再出现明显的「缓存刷新」等待。

- 新增：
  - 冷启动埋点 `[COLDSTART]`（Debug 构建）：记录 early-list 是否发出/被闸门跳过、`session/list` 请求与落地耗时、in-flight 超时重发等，便于后续现场归因。
- 改进：
  - **连接提速**：跨网（蜂窝/不同网络）时 relay 候选立即拨号，不再先串行等待 mDNS 发现 + 并行 `/health` 探测（真机实测 1.58 秒）；API token 与 mux token 两轮认证并行；WSS 的 TCP+TLS 提前建立、token 到位立即升级；`$events` ready 移到连接完成后的后台握手。真机 10 次冷启动 **626–722ms（中位 665.5ms，10/10 <1s）**。
  - **列表刷新提速**：early `session/list` 在持久化地址是失效 LAN 时改用可达的 relay 候选；增加 400ms→5s 的有界重试并在请求挂起 >1.2s 时并行重发；冷启动预热 HTTPS 共享连接池。真机 T2（列表就绪）中位 **851.9ms**（8/10 <1s，较上一版 −131ms）。
  - **缓存刷新提示更克制**：「本地缓存 · 正在刷新…」延迟 800ms 才显示，低于此阈值的刷新用户完全不可见；从会话详情返回列表时不再出现该提示（494ms 内完成）。
  - 切网恢复：模拟网络切换后 **≈0.7 秒**恢复（上一版 2.1–2.5 秒）。
- 修复：
  - 修复冷启动「连接中」持续 2–3 秒的问题（现中位 0.67 秒、最差 0.72 秒）。
  - 修复「桌面端重启后首次启动」类场景下列表可能长时间停留在「本地缓存 · 正在刷新…」的问题（连接慢启动窗口内列表现在自带重试，不被 20 秒 unary 超时拖住）。
  - 修复连接完成时触发的重新加载会取消已接近完成的早期列表请求、导致整轮重发的问题。
- 已知限制：
  - T2 慢样本仍约 1.07 秒（中继往返抖动，非本地逻辑），中位已 <1s。
  - 5G 经中继的 TLS/认证物理成本约 0.5 秒，连接时延已接近该链路下限。
  - 会话详情首帧仍受既存窗口缓存恢复耗时影响（约 0.24–1.1 秒，随缓存内容变化），属于后续「全量历史自动加载」迭代的优化范围。
  - 插件为 v0.2.5（本版插件代码仅版本号变化，无行为改动）；若桌面端尚未重启到 v0.2.4 的 LAN 端点修复，请重启以生效。

## English

DSH-m v0.2.5 is a cold-start and list-refresh performance release: in a real 5G scenario where the phone and the Mac are on different networks, "connecting → online" drops from 2.4–2.7s to **0.63–0.72s (10/10 runs under 1s)**, and the workspace list is ready within ~1s without a visible "cache refreshing" wait.

- New:
  - `[COLDSTART]` diagnostics (debug builds): whether the early-list request was sent or gated, the `session/list` request/apply timing, and in-flight timeout re-issues — for field attribution.
- Improvements:
  - **Faster connect**: on cellular / cross-network paths the relay candidate is dialed immediately instead of first waiting for mDNS discovery + parallel `/health` probes (measured 1.58s on device); the API token and mux token handshakes run in parallel; the WSS TCP+TLS connection is pre-established and upgraded as soon as the token arrives; the `$events` ready handshake moves to the background after connect. Measured over 10 cold starts: **626–722ms (median 665.5ms, 10/10 <1s)**.
  - **Faster list refresh**: the early `session/list` uses a reachable relay origin when the persisted origin is a stale LAN address; bounded retries (400ms→5s) with a parallel re-issue when a request hangs for >1.2s; the shared HTTPS pool is warmed during cold start. Measured T2 (list ready): median **851.9ms** (8/10 <1s, −131ms vs the previous build).
  - **Less intrusive cache indicator**: "本地缓存 · 正在刷新…" only appears after 800ms, so a sub-threshold refresh is invisible; returning from a session detail no longer shows it (completes in 494ms).
  - Network-switch recovery: **≈0.7s** after a simulated switch (previously 2.1–2.5s).
- Fixes:
  - Fixed the 2–3s "connecting" phase on cold start (now median 0.67s, worst 0.72s).
  - Fixed the workspace list getting stuck on "本地缓存 · 正在刷新…" in first-launch-after-desktop-restart scenarios (the list now retries during a slow connect window instead of waiting out a 20s unary timeout).
  - Fixed the connected/generation reload cancelling a nearly-finished early list request and re-issuing the whole round.
- Known limitations:
  - Slow T2 samples are still ~1.07s (relay round-trip jitter, not local logic); the median is under 1s.
  - The 5G relay path has a physical TLS/auth cost of about 0.5s; connect latency is now close to that link's floor.
  - Session-detail first frame is still affected by the existing window-cache restore cost (~0.24–1.1s depending on cache content); that belongs to the upcoming full-history autoload iteration.
  - The plugin is v0.2.5 (this release changes the plugin version only, no behaviour change); if the desktop app has not been restarted onto the v0.2.4 LAN-endpoint fix yet, restart it for that fix to take effect.
