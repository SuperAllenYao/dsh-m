# DSH-m v0.2.6

## 中文

DSH-m v0.2.6 是「全量历史自动加载 + 滚动底座重构」版本：打开会话详情后无条件把全部历史自动补到最早一条，并把消息列表从 SwiftUI ScrollView 换成 **UIKit 反转列表（UITableView + scaleY(-1)）+ 布局期锚定**。真机自动化实测（真实手势、生产 env、帧级探针）：历史补齐 22/22 批插入时锚点行屏幕位移 **0.0pt**（最大 4e-5pt），静止窗口内可见行位移 **0.0pt**，无内容整体替换帧；补齐期间主线程耗时热点（历史页解码、窗口缓存写盘）已移出主线程，**Release 构建真机手点快速滑动顺滑**。

- 新增：
  - **全量历史自动加载**：进入会话详情即后台向前翻页直到最早一条，全程无按钮、无文案、无进度、无菊花；补齐完成后 `oldest=0 / holes=0`（本机 11.07MB / 815 行真实会话实测完成，8 页约 6–9 秒）。
  - **消息列表 UIKit 反转底座**：`UITableView` 整体翻转 + cell 翻回，数据源新→旧排列，历史补齐 = 向数据源尾部追加，已有内容 content 坐标不变；行视图复用现有 SwiftUI（`UIHostingConfiguration`）。
  - **布局期锚定兜底**：每次布局（屏幕提交前）按锚点行真实 frame 校正 contentOffset，不依赖行高估算。
  - **贴底语义三件套**：贴底时新内容直接出现在底部；读历史时新消息先冻结、回到底部一次性出现；发送消息后强制回到底部（读历史时也能立刻看到自己刚发的消息）。
  - **键盘/内联视口高度变化**时保持读历史的阅读位置，不再整体上跳再跳回。
  - 首屏缓存升级（FirstPaintCache v5）、`FlowState` 增量渲染、`DetailMetrics` 首屏计时（tapMs/shellMs/contentMs/cacheMs/fillMs/fillPages/fillOldest）。
- 改进：
  - **滚动卡顿修复（真机手点定位）**：`JSONValue.decode` 内部是「JSON 重编码 → 目标类型解码」的双重转换，历史页/snapshot/大事件解码原本在 main actor（实测单页 111–466ms）→ 全部移到后台队列（历史页pageDecodeBG、stream frame 串行 FIFO 保持顺序）。
  - 补齐期间不再逐批写窗口缓存（每批约 4MB JSON 编码 + 原子写，主线程 ~29ms）；缓存写入改后台队列 + 只保留最新一次，补齐完成/离开时统一写。
  - 补齐批次逐批发布（不再延迟到补齐完成），补齐期间可正常滚动阅读。
  - 真机测量基建修正：帧级探针只统计 `UITableView.visibleCells`（真正参与渲染的 cell），使用反转列表的正确坐标模型；新增 CA 提交后复核（`commitCheck`）区分「布局中间态」与「真实上屏」。
- 修复：
  - 修复补齐插入导致内容跳变（旧 SwiftUI 实现逐批插入单批可见位移 1871–4851pt，现为 0）。
  - 修复读历史时发送消息看不到自己刚发消息的问题（发送后强制回底）。
  - 修复键盘弹出时读历史内容整体跳动的问题。
  - 修复冷缓存首开详情约 2 秒空白的问题（壳 18.7ms、首个内容 606.7ms，期间为骨架占位；热缓存首个内容 266.9–285.4ms）。
  - 修复 **Release 构建编译失败**（DEBUG-only 帧级探针协议被生产代码无条件遵循）。
  - 沿用前几轮修复：补齐瞬时错误有界重试、旧 schema 缓存静默丢弃、「正在刷新」横幅不再卡死。
- 已知限制：
  - **Debug 构建**下大会话快速滑动仍有布局开销（SwiftUI/Markdown 未优化路径，实测单次 layout pass 最高约 70ms）；**Release 构建真机手点已明显顺滑**，验收/交付请使用 Release 构建。
  - E2E 插桩（`DSHM_E2E=1` / `DSHM_JITTERDBG=1` / `DSHM_PERFDBG=1`）会放大渲染瞬态，仅测试环境出现，生产构建零开销。
  - 补齐期间历史逐批出现；超出已缓存窗口的更早历史要等补齐推进到该批才可见。
  - 16.7MB 超大历史会话、运行中会话（流式）在补齐期间的交互未纳入本轮自动化，建议真机手点确认。
  - 插件为 v0.2.6（本版插件仅版本号变化，无行为改动）；桌面端需重启后加载新版本号。

## English

DSH-m v0.2.6 is the "full-history autoload + scroll foundation rework" release: opening a session detail now unconditionally backfills the entire history to the earliest event, and the message list moves from SwiftUI ScrollView to a **UIKit reversed list (UITableView + scaleY(-1)) with layout-time anchoring**. On-device automation (real gestures, production env, frame-level probe): across **22/22 history-insert batches the anchor row's on-screen displacement was 0.0pt** (max 4e-5pt), visible-row displacement in idle windows was 0.0pt, and no identity-replacement frames were observed. The main-thread hotspots during backfill (history page decoding, window-cache writes) were moved off the main thread, and **fast scrolling is smooth on a Release build in real hand testing**.

- New:
  - **Full-history autoload**: entering a session detail backfills until the earliest event in the background — no buttons, copy, progress or spinners; on completion `oldest=0 / holes=0` (verified on a real 11.07MB / 815-row session; 8 pages in ~6–9s).
  - **UIKit reversed message list**: the `UITableView` is flipped with cells flipped back and the data source ordered newest→oldest, so history backfill appends to the data-source tail and existing content coordinates never change; row views reuse the existing SwiftUI views via `UIHostingConfiguration`.
  - **Layout-time anchoring**: on every layout pass (before the frame commits) the content offset is corrected from the anchor row's real frame — no row-height estimation involved.
  - **Pinned-to-bottom semantics**: new content appears at the bottom immediately while pinned; while reading history new tail content is frozen and applied in one pass on return to the bottom; sending a message always forces the list back to the bottom so the user sees their own message.
  - Viewport-height changes (keyboard show/hide, inline rows) no longer shift the reading position while browsing history.
  - FirstPaintCache v5, `FlowState` incremental rendering, and `DetailMetrics` first-paint timing (tapMs/shellMs/contentMs/cacheMs/fillMs/fillPages/fillOldest).
- Improvements:
  - **Scroll-stutter fixes (located with real hand testing)**: `JSONValue.decode` internally re-encodes to JSON and decodes again; history pages/snapshots/large events were decoded on the main actor (111–466ms per page measured) → all moved to background queues (history pages via pageDecodeBG, stream frames via an ordered FIFO decoder).
  - The window cache is no longer written per backfill batch (~4MB JSON encode + atomic write, ~29ms on the main thread each time); cache writes are queued in the background and coalesced to the latest payload, with a final write when the fill completes or the detail closes.
  - History batches are published incrementally (no longer deferred until completion), so scrolling during the backfill stays usable.
  - Measurement infrastructure fixes: the frame probe now only tracks `UITableView.visibleCells` with the correct coordinate model for a reversed list, plus a post-CA-commit recheck to separate transient layout states from what is really presented.
- Fixes:
  - Fixed content jumping caused by history insertion (the old SwiftUI implementation moved 1871–4851pt per batch; now 0).
  - Fixed not seeing your own message when sending while reading history (sending now forces the list to the bottom).
  - Fixed content jumping on keyboard appearance while reading history.
  - Fixed the ~2s blank content area when opening a detail with a cold cache (shell 18.7ms, first content 606.7ms with a skeleton placeholder; hot cache first content 266.9–285.4ms).
  - Fixed the **Release build failing to compile** (a DEBUG-only frame-probe protocol was unconditionally adopted by production code).
  - Carried over from earlier rounds: bounded retries for transient backfill errors, silent discard of legacy cache schemas, and the "refreshing" banner no longer sticking forever.
- Known limitations:
  - On **Debug builds**, fast scrolling in large sessions still pays layout cost (unoptimized SwiftUI/Markdown paths; single layout pass up to ~70ms measured). **Release builds are smooth in real hand testing**; use a Release build for acceptance and delivery.
  - E2E instrumentation (`DSHM_E2E=1` / `DSHM_JITTERDBG=1` / `DSHM_PERFDBG=1`) amplifies render transients; it only affects test builds and is zero-cost in production.
  - History appears batch by batch during the backfill; history beyond the cached window becomes visible only when the fill reaches it.
  - The 16.7MB extreme session and interactions with a running (streaming) session during backfill were not automated in this round; a manual device check is recommended.
  - The plugin is v0.2.6 (version bump only, no behaviour change); restart the desktop app to pick it up.
